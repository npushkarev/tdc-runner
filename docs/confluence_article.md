# Интеграционные тесты в Docker: что нужно от вашего репозитория

Для команд, чьи компоненты будут тестироваться автоматически.

Здесь требования и правила. Пошаговая инструкция с примерами лежит в
[HOWTO](HOWTO.md). Разбор того, как это вышло на живом .NET-проекте, в
[отдельной статье](case_dotnet_openide.md).

Вопросы и случаи «а у меня не так»: `<канал, чат или почта: заполнить>`.

---

## 1. Зачем

Сейчас интеграционные тесты у большинства команд запускаются руками. Надо
поставить Docker, скопировать `.env`, поправить подсети, вспомнить команду.
На выходе только «упало или не упало». В CI такие тесты не запускаются.

Теперь вы один раз описываете, что нужно вашим тестам: какие сервисы рядом,
какие файлы, сколько ждать. Дальше система сама запускает их, забирает
результаты и всё за собой удаляет. Одинаково для C++ и .NET.

## 2. Подойдёт ли вам это сейчас

| Что | Ответ |
|---|---|
| ОС и архитектура | Linux, x64 |
| Когда запускается | после коммита. Конфигурация в TeamCity сейчас настраивается |
| Тесты работают внутри контейнера | да |
| Тесты сами создают контейнеры (Testcontainers, Docker API) | нет |
| Windows | второй этап |
| arm, arm64 | механика готова, ждём образы под эти архитектуры |
| Пароли файлами | да, см. §7 |

Ваш случай не подошёл: напишите нам.

## 3. Что положить в репозиторий

Скачайте инструмент один раз:

```sh
git clone <адрес репозитория tdc-runner>
```

Скопируйте из него шаблон под свой стек в корень своего репозитория:

```sh
cp -r tdc-runner/templates/dotnet/test_docker_config <ваш репозиторий>/
# или templates/cpp
```

Получится:

```
test_docker_config/
  post_commit/
    integration/
      docker-compose.yml
      .env.default
      test_cfg.xml
```

`post_commit` это когда запускать. Пока поддерживается только такой вариант.

`integration` это имя набора. Можно переименовать: маленькие латинские буквы,
цифры, подчёркивание. Например `integration`, `billing_db`, `api_smoke`.
Наборов может быть несколько, каждый в своей папке.

В шаблоне помечено словом `ЗАМЕНИТЬ`. Остальное рабочее.

### docker-compose.yml

Обычный Docker Compose. Один сервис это ваши тесты. Остальные это то, что им
нужно рядом: база, брокер, заглушка стороннего сервиса.

Образ с вашими тестами должен быть собран заранее и лежать в ProGet с
конкретным тегом. Собирает его отдельная конфигурация сборки. Как это устроить
для вашего компонента, согласуйте с нами. Пока это делается индивидуально.

Что в compose запрещено, смотрите в §8. Шаблоны этому уже соответствуют.

### .env.default

Обычные `КЛЮЧ=значение`. Файл лежит в git, поэтому настоящих паролей и ключей
в нём быть не должно. Тестовые заглушки вроде `POSTGRES_PASSWORD=test` можно.

Имена с префиксами `TEST_`, `BUILD_`, `VCS_`, `COMPOSE_`, `DOCKER_` заняты
системой.

### test_cfg.xml

```xml
<?xml version="1.0" encoding="UTF-8"?>
<test_cfg version="1">
  <meta>
    <description>Интеграционные тесты My.Component</description>
  </meta>

  <environment>
    <os>linux</os>
    <arch>x64</arch>
  </environment>

  <outputs>
    <report type="tests" format="trx" path="results/**/*.trx"/>
  </outputs>

  <execution>
    <main_service>tests</main_service>
    <timeout_minutes>20</timeout_minutes>
  </execution>
</test_cfg>
```

| Блок | Что задаёт |
|---|---|
| `<environment>` | на какой ОС и архитектуре набор можно запускать |
| `<outputs>` | что забрать после прогона. Пути считаются от `/test/output` |
| `<execution>` | какой сервис это тесты и через сколько минут его остановить |

Ещё три блока нужны не всем, они описаны в §7: `<inputs>`, `<secrets>`,
`<privileges>`.

## 4. Два правила, из-за которых чаще всего не работает

**Отчёты пишите в `/test/output`.** Только этот каталог переживёт контейнер.
Файлы в других местах пропадут. В шаблонах нужные ключи уже стоят.

**К соседним сервисам обращайтесь по имени из compose.** Не по `localhost`.
Если рядом база с именем `postgres`, то хост подключения будет `postgres`.

Чтобы тесты не стартовали раньше, чем готова база, опишите у базы
`healthcheck`, а у тестов `depends_on` с `condition: service_healthy`. Система
ждёт именно готовности по healthcheck.

Сам код тестов переписывать не нужно. Но если сейчас тесты ходят на `localhost`
или кладут отчёты рядом с собой, эти два места в их настройках придётся
поправить.

## 5. Как проверить у себя до коммита

Нужны только `docker` и `python3`. Команды запускаются из каталога
`tdc-runner`:

```sh
# быстрая проверка файлов, контейнеры не поднимаются
python3 -m tdc validate --repo <ваш репозиторий>

# полный прогон на своей машине, тем же кодом, что и на сервере
./run_local.sh <имя набора> --repo <ваш репозиторий>

# если набор берёт файлы из артефактов сборки, добавьте каталог с ними
./run_local.sh <имя набора> --repo <ваш репозиторий> --artifacts <каталог>
```

Всё хорошо, если команда завершилась без ошибок и появился каталог с отчётами.
По умолчанию это `.tdc-out/` внутри вашего репозитория. Добавьте его в
`.gitignore`.

Валидация ругается коротким кодом, например `compose.build_forbidden`.
Расшифровка всех кодов есть в [HOWTO](HOWTO.md).

## 6. Что вы получите

После каждого прогона:

```
reports/<имя набора>/
  tests/       результаты тестов
  coverage/    покрытие, если вы его собираете
  _infra/      логи всех контейнеров и их состояние
```

Результаты тестов и цифры покрытия публикуются в интерфейсе сборки.
`_infra/` смотрите первым делом при падении. Он сохраняется всегда, даже если
прогон развалился на середине.

Типы отчётов, которые система понимает: результаты тестов (`trx`, `junit`),
покрытие (`cobertura`), снапшоты, статический анализ. Нужен другой тип:
напишите, добавим. Пока такой отчёт просто сохранится файлом и прогон не
сломает.

## 7. Особые случаи

### Тестам нужны файлы снаружи

По умолчанию внутрь контейнера не попадает ничего. Ни исходники, ни артефакты
сборки. Нужное перечисляется явно:

```xml
  <inputs>
    <artifact path="build/tests/**" dest="bin/"/>
    <source path="tests/data/**" dest="data/"/>
  </inputs>
```

`artifact` берётся из опубликованных артефактов сборки. `source` из вашего
репозитория. `dest` это куда положить внутри `/test/input`.

Путь сохраняется от первой статической части маски. Для `build/tests/**` файлы
лягут прямо в `/test/input/bin`. Для `**/tests/**` сохранится всё дерево.

### Контейнер не стартует под изоляцией

Мы снимаем с контейнеров все системные права. Из-за этого некоторые образы не
запускаются. Например, база при первом запуске создаёт свой каталог данных и
переключает пользователя. Признак: в логах сообщение вроде
`failed switching to 'postgres'`.

Верните ей нужный минимум:

```xml
  <privileges>
    <service name="postgres" cap_add="CHOWN DAC_OVERRIDE FOWNER SETGID SETUID"/>
  </privileges>
```

Этих пяти хватает базам PostgreSQL. Всего разрешено восемь: перечисленные плюс
`FSETID`, `KILL`, `NET_BIND_SERVICE`.

### Пароли

В `.env.default` их класть нельзя, этот файл лежит в git. Объявите в паспорте:

```xml
  <secrets>
    <secret name="db_password" services="postgres"/>
  </secrets>
```

Значение приедет файлом в `/test/secrets/db_password`. Только на чтение и
только тем сервисам, что перечислены в `services=`. Не указали: увидит только
главный сервис. Многие образы умеют читать пароль из файла, ищите переменные
вида `POSTGRES_PASSWORD_FILE`. В переменные окружения значение не попадает.

Файлы кладёт отдельный шаг сборки, финальная уборка их стирает. Локально
каталог передаётся ключом `--secrets <каталог>`.

Если секрет объявлен, но не выложен, прогон не начнётся. Так задумано. Пустое
значение внутри контейнера выглядело бы как загадочное падение тестов.

## 8. Что в compose запрещено

| Нельзя | Почему |
|---|---|
| `build:` | тестовая машина не должна собирать образы и получать исходники |
| проброс папок с хоста | доступ к файловой системе машины |
| `ports:` | занятые порты и конфликты между параллельными запусками |
| `container_name:` | два запуска одновременно не уживутся |
| `restart:` | упавшую базу не нужно поднимать бесконечно |
| `privileged`, `cap_add`, `devices` | обход изоляции |
| сеть, PID или IPC хоста | выход за пределы контейнера |
| образы не из ProGet, тег `latest` | чтобы повторный запуск давал тот же результат |

Проверяется автоматически, до запуска контейнеров.

## 9. Чек-лист

- [ ] скопирован шаблон под ваш стек, заменено помеченное
- [ ] образ лежит в ProGet с конкретным тегом. Для .NET это образ с вашими
      тестами. Для C++ это рантайм, а бинарники приезжают через `<inputs>`
- [ ] отчёты пишутся в `/test/output`
- [ ] к соседним сервисам обращаемся по имени из compose
- [ ] в `.env.default` нет настоящих паролей
- [ ] `python3 -m tdc validate` даёт `OK`
- [ ] `./run_local.sh` проходит локально
- [ ] три файла закоммичены, `.tdc-out/` добавлен в `.gitignore`
