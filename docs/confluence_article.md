# Интеграционные тесты в Docker: что нужно от вашего репозитория

Для команд, чьи компоненты будут тестироваться автоматически. Отвечает на два
вопроса: **что положить в репозиторий** и **что вы за это получите**.

Пошаговый маршрут с готовыми примерами — в [HOWTO](HOWTO.md). Разбор того,
как это вышло на настоящем .NET-проекте, — в [отдельной
статье](case_dotnet_openide.md). Эта — требования и правила.

**Вопросы, случаи «а у меня не так», просьбы добавить формат отчёта:**
`<канал/чат/почта — заполнить>`.

---

## 1. Зачем

Сейчас интеграционные тесты у большинства команд запускаются руками: поставить
Docker, скопировать `.env`, поправить подсети, вспомнить нужную команду.
Результатов на выходе нет — только «упало / не упало». В CI такие тесты не
запускаются вообще.

Теперь вы один раз пишете, что нужно вашим тестам: какие сервисы рядом, какие
файлы, сколько ждать. Дальше система сама запускает их после коммита, забирает
результаты и всё за собой удаляет. Одинаково для C++ и .NET.

## 2. Подойдёт ли вам это сейчас

| Условие | Сейчас |
|---|---|
| ОС и архитектура | Linux, x64 |
| Когда запускается | после коммита (конфигурация в TeamCity сейчас заводится) |
| Тесты выполняются внутри контейнера | да |
| Тесты сами создают контейнеры (Testcontainers, Docker API) | **не поддерживается** |
| Windows | следующий этап |
| arm, arm64 | механика готова, ждём образы под эти архитектуры |
| Доставка паролей файлами | да, см. §7 |

Если ваш случай не подходит — напишите нам, посмотрим вместе.

## 3. Что положить в репозиторий

Инструмент лежит отдельно, склонируйте один раз:

```sh
git clone <адрес репозитория tdc-runner>
```

Скопируйте из него готовый шаблон под свой стек в корень своего репозитория:

```sh
cp -r tdc-runner/templates/dotnet/test_docker_config <ваш репозиторий>/
# или templates/cpp
```

Получится:

```
test_docker_config/
  post_commit/
    integration/
      docker-compose.yml
      .env.default
      test_cfg.xml
```

- `post_commit` — когда запускать. Пока поддерживается только этот вариант.
- `integration` — имя набора, можно переименовать: маленькие латинские буквы,
  цифры, подчёркивание. Например `integration`, `billing_db`, `api_smoke`.
  Наборов может быть несколько, каждый в своей папке и запускается отдельно.

В шаблоне заменить помечено словом `ЗАМЕНИТЬ`. Остальное — рабочее.

### `docker-compose.yml` — из чего состоит окружение

Обычный Docker Compose. Один сервис — ваши тесты, остальные — то, что им нужно
рядом: база, брокер, заглушка стороннего сервиса.

**Образ с вашими тестами должен быть собран заранее и лежать в ProGet с
конкретным тегом.** Собирает его отдельная конфигурация сборки — как это
устроено для вашего компонента, согласуйте с нами: сейчас это делается
индивидуально.

Список того, что в compose запрещено, — в §8. Шаблоны ему уже соответствуют,
так что при копировании шаблона вы с этим не столкнётесь.

### `.env.default` — значения по умолчанию

Обычные `КЛЮЧ=значение`. Файл лежит в git, поэтому **настоящих паролей и ключей
в нём быть не должно**. Тестовые заглушки вроде `POSTGRES_PASSWORD=test`,
которые не дают доступа никуда за пределы прогона, — нормально.

Имена, начинающиеся с `TEST_`, `BUILD_`, `VCS_`, `COMPOSE_`, `DOCKER_`, заняты
системой.

### `test_cfg.xml` — настройки набора

```xml
<?xml version="1.0" encoding="UTF-8"?>
<test_cfg version="1">
  <meta>
    <description>Интеграционные тесты My.Component</description>
  </meta>

  <environment>
    <os>linux</os>
    <arch>x64</arch>
  </environment>

  <outputs>
    <report type="tests" format="trx" path="results/**/*.trx"/>
  </outputs>

  <execution>
    <main_service>tests</main_service>
    <timeout_minutes>20</timeout_minutes>
  </execution>
</test_cfg>
```

| Блок | Что означает |
|---|---|
| `<environment>` | на какой ОС и архитектуре набор можно запускать |
| `<outputs>` | что забрать после прогона; пути считаются от `/test/output` |
| `<execution>` | какой сервис — это тесты (завершился успешно, значит набор прошёл) и через сколько минут его остановить |

Ещё два блока нужны не всем, они описаны в §7: `<inputs>` — если тестам нужны
файлы снаружи, `<privileges>` — если контейнер не стартует под изоляцией.

## 4. Два правила, из-за которых чаще всего не работает

**Отчёты пишите в `/test/output`.** Это единственный каталог, который переживёт
контейнер; всё остальное исчезнет вместе с ним. В шаблонах нужные ключи уже
проставлены.

**К соседним сервисам обращайтесь по имени из compose, а не через `localhost`.**
Если рядом база с именем `postgres`, то хост подключения — `postgres`.

Чтобы тесты не стартовали раньше, чем база готова, опишите у неё `healthcheck`,
а у тестов — `depends_on … condition: service_healthy`. В шаблоне с базой это
уже сделано; без этого система ждать готовности не сможет — она смотрит именно
на healthcheck.

Сам код тестов переписывать не нужно. Но если сейчас они ходят на `localhost`
или складывают отчёты рядом с собой — эти два места в их настройках поправить
придётся.

## 5. Как проверить у себя до коммита

Нужны только `docker` и `python3`. Из каталога `tdc-runner`:

```sh
# быстрая проверка файлов, контейнеры не поднимаются
python3 -m tdc validate --repo <ваш репозиторий>

# полный прогон на своей машине — тем же кодом, что и на сервере
./run_local.sh <имя набора> --repo <ваш репозиторий>

# если набор берёт файлы из артефактов сборки (<inputs>), добавьте каталог с ними
./run_local.sh <имя набора> --repo <ваш репозиторий> --artifacts <каталог>
```

Всё хорошо, если команда завершилась без ошибок и появился каталог с отчётами.
По умолчанию это `.tdc-out/` внутри вашего репозитория — добавьте его в
`.gitignore`.

Если валидация ругается — она называет причину коротким кодом
(`compose.build_forbidden`, `env.reserved_prefix` и подобными). Расшифровка всех
кодов и что с ними делать — в [HOWTO](HOWTO.md).

## 6. Что вы получите

После каждого прогона:

```
reports/<имя набора>/
  tests/       результаты тестов
  coverage/    покрытие — если вы его собираете
  _infra/      логи всех контейнеров и их состояние
```

Результаты тестов и цифры покрытия публикуются в интерфейсе сборки. `_infra/` —
первое, куда смотреть при падении: он сохраняется всегда, даже если прогон
развалился на середине.

Типы отчётов, которые система понимает и показывает: **результаты тестов**
(`trx`, `junit`), **покрытие** (`cobertura`), **снапшоты**, **статический
анализ**. Если вам нужен тип, которого здесь нет, — напишите, добавим; пока
такой отчёт просто сохранится файлом и прогон не сломает.

## 7. Особые случаи

### Тестам нужны файлы снаружи

По умолчанию внутрь контейнера **не попадает ничего** — ни исходники, ни
артефакты сборки. Нужное перечисляется явно:

```xml
  <inputs>
    <artifact path="**/tests/**" dest="bin/"/>
    <source path="tests/data/**" dest="data/"/>
  </inputs>
```

`artifact` — из опубликованных артефактов сборки, `source` — из вашего
репозитория, `dest` — куда внутри `/test/input`. Если в путях артефактов есть
метки ОС и архитектуры, система отсеет чужие — но полагаться только на это не
стоит: маска ваша, и отвечает за неё тоже она.

### Контейнер не стартует под изоляцией

Мы снимаем с контейнеров все системные привилегии. Из-за этого некоторые образы
не запускаются: например, база при первом запуске создаёт свой каталог данных и
переключает пользователя. Признак — сообщение вроде
`failed switching to 'postgres'` в логах. Верните ей нужный минимум:

```xml
  <privileges>
    <service name="postgres" cap_add="CHOWN DAC_OVERRIDE FOWNER SETGID SETUID"/>
  </privileges>
```

Эти пять хватает базам PostgreSQL. Разрешены только они и ещё три: `FSETID`,
`KILL`, `NET_BIND_SERVICE`.

### Пароли

В `.env.default` их класть нельзя — этот файл лежит в git. Объявите в паспорте:

```xml
  <secrets>
    <secret name="db_password" services="postgres"/>
  </secrets>
```

Значение приедет **файлом** в `/test/secrets/db_password`: только на чтение и
только тем сервисам, что перечислены в `services=` (если не указать — только
главному). Многие образы умеют читать пароль из файла — переменные вида
`POSTGRES_PASSWORD_FILE`. В переменные окружения значение не попадает.

Кладёт файлы отдельный шаг сборки, финальная уборка их стирает. Локально
каталог передаётся ключом `--secrets <каталог>`.

Если секрет объявлен, но не выложен, прогон не начнётся — так задумано: пустое
значение внутри контейнера выглядело бы как загадочное падение тестов.

## 8. Что в compose запрещено

| Нельзя | Почему |
|---|---|
| `build:` | тестовая машина не должна собирать образы и получать исходники |
| проброс папок с хоста | доступ к файловой системе машины |
| `ports:` | занятые порты и конфликты между параллельными запусками |
| `container_name:` | два запуска одновременно не уживутся |
| `restart:` | упавшую базу не нужно поднимать бесконечно |
| `privileged`, `cap_add`, `devices` | обход изоляции |
| сеть, PID или IPC хоста | выход за пределы контейнера |
| образы не из ProGet, тег `latest` | чтобы повторный запуск давал тот же результат |

Проверяется автоматически, до запуска контейнеров.

## 9. Чек-лист

- [ ] скопирован шаблон под ваш стек, заменено помеченное
- [ ] образ лежит в ProGet с конкретным тегом (для .NET — с вашими тестами,
      для C++ — рантайм, а бинарники приезжают через `<inputs>`)
- [ ] отчёты пишутся в `/test/output`
- [ ] к соседним сервисам — по имени из compose
- [ ] в `.env.default` нет настоящих паролей
- [ ] `python3 -m tdc validate` даёт `OK`
- [ ] `./run_local.sh` проходит локально
- [ ] три файла закоммичены, `.tdc-out/` добавлен в `.gitignore`
