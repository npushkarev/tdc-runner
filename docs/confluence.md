# Автотесты в Docker после сборки

Текст этой страницы кладётся в Confluence как есть. Схема к разделу «Как это
работает»: `schemes/in662_howto_overview.png`.

## Коротко

Вы кладёте в свой репозиторий три файла. Дальше всё происходит само: тесты
запускаются в контейнере, отчёты собираются наружу, мусор убирается. Код тестов
менять не надо.

Нужны только `docker` и `python3`.

## Что уже сделано

- Есть пускалка. Один и тот же код гоняет тесты и у вас на машине, и на
  сервере. Прошло у вас, пройдёт и там.
- Есть шаблоны для .NET и C++. Из них конфигурация делается копированием.
- Проверено на живом проекте. `SCADA/elara_openide_backend`, набор
  интеграционных тестов на PostgreSQL: тесты проходят, отчёты и покрытие
  собираются, после прогона на машине не остаётся ни контейнеров, ни томов.
- Опасные вещи запрещены до запуска. Сборка образа внутри теста, проброс папок
  с хоста, порты наружу, образы не из ProGet. Проверка идёт до старта
  контейнеров, а не после падения.

Чего пока нет: запуска по кнопке в TeamCity, Windows и arm. Это следующий шаг.

## Подходит ли вам

| Вопрос | Ответ |
|---|---|
| ОС и архитектура контейнеров | Linux x64 |
| Тесты работают внутри контейнера | да |
| Тесты сами создают контейнеры (Testcontainers, Docker API) | нет, пока не поддерживается |
| Windows, arm | позже |

## Что лежит в архиве

Скачали zip с проектом, распаковали, увидели десяток папок. Нужны вам из них
три, остальное можно не открывать.

| Что | Зачем |
|---|---|
| `run_local.sh` | **пускалка.** Единственное, что вы запускаете руками |
| `templates/` | **заготовки** для .NET и C++. Отсюда копируется конфигурация в ваш репозиторий |
| `docs/` | **документация.** Эта статья и документ про устройство системы |
| `tdc/` | код пускалки на python. Работает сам, трогать не надо |
| `vendor/compose/` | docker compose нужной версии для машин, где его нет в системе |
| `smoke/` | демонстрация на готовом примере: `./smoke/demo_from_template.sh` |
| `profiles/` | живой пример: конфигурация, сделанная для OpenIde |
| `tests/` | тесты самой пускалки. К вашим тестам отношения не имеют |
| `ci/` | шаг запуска для сервера сборки. Вручную не нужен |
| `schemes/` | картинки для документации |

Ничего устанавливать не надо: ни pip, ни виртуального окружения. Нужны только
`docker` и `python3` в системе.

## Как завести свои тесты

### Шаг 1. Возьмите шаблон

```sh
git clone <адрес tdc-runner>
cd tdc-runner
cp -r templates/dotnet/test_docker_config <ваш репозиторий>/
```

Для C++ вместо `dotnet` берите `cpp`.

В вашем репозитории появится:

```
test_docker_config/post_commit/integration/
    docker-compose.yml    что поднимать
    .env.default          значения по умолчанию, без паролей
    test_cfg.xml          что запускать и какие отчёты забрать
```

### Шаг 2. Замените отмеченное

В файлах помечено словом ЗАМЕНИТЬ. Кроме этих мест ничего не трогайте.

| Файл | Что заменить |
|---|---|
| `docker-compose.yml`, `image:` | ваш образ в ProGet, тег конкретный, не `latest` |
| `docker-compose.yml`, `command:` | путь к тест-проекту (.NET) или имя бинарника (C++) |
| `docker-compose.yml`, `--filter` | как помечены ваши интеграционные тесты |
| `test_cfg.xml`, `<description>` | одна строка про набор |
| `test_cfg.xml`, `<timeout_minutes>` | если тесты идут дольше 20 минут |

Образ с вашими собранными тестами публикует отдельная конфигурация сборки.
Как это устроить для вашего компонента, спросите у нас.

### Шаг 3. Проверьте два правила

**Отчёты пишите в `/test/output`.** Только этот каталог переживает контейнер.
В шаблонах нужные ключи уже стоят.

**К соседям обращайтесь по имени сервиса, не по `localhost`.** Рядом база с
именем `postgres`, значит хост будет `postgres`.

Частая засада: в настройках тестов лежит `localhost` по умолчанию. Адрес должен
браться из переменной окружения.

### Если рядом нужна база

Добавьте в `test_cfg.xml`, иначе postgres не стартует под снятыми правами:

```xml
  <privileges>
    <service name="postgres" cap_add="CHOWN DAC_OVERRIDE FOWNER SETGID SETUID"/>
  </privileges>
```

В самом compose `cap_add` запрещён: там можно попросить что угодно. В манифесте
список закрытый.

### Если нужны пароли

В `.env.default` их писать нельзя, файл лежит в git. Объявляйте секрет:

```xml
  <secrets>
    <secret name="db_password" services="postgres"/>
  </secrets>
```

Он приедет файлом в `/test/secrets/db_password`, только на чтение и только
перечисленным сервисам.

## Как запустить

```sh
cd tdc-runner
./run_local.sh integration --repo <ваш репозиторий>
```

`integration` это имя папки вашего набора. Ошиблись в имени, пускалка напечатает
список доступных.

Что увидите:

```
integration: passed (main service exit code 0)
  тесты: 7 прошло, 0 упало, 0 пропущено
  покрытие: строки 238/4307 (5.53%), ветви 18/1300 (1.38%)
  отчёты: <ваш репозиторий>/.tdc-out/reports/integration
    tests/results/integration.trx
    coverage/results/8f21.../coverage.cobertura.xml
    _infra/ — логи контейнеров и вывод compose
```

### Нужен ли python3, если запускать вручную

Нет. Для ручного запуска через `docker compose` python3 не нужен, ваши
существующие compose-файлы работают как работали.

python3 нужен только пускалке. Она делает то, чего `docker compose` сам не
делает: проверяет конфигурацию до старта контейнеров, накладывает ограничения
и монтирования, забирает отчёты наружу, прибирает контейнеры и тома.

Наш файл руками тоже запускается, но нужны два дополнения:

```sh
cd test_docker_config/post_commit/<набор>
mkdir -p out
docker compose --env-file .env.default run --rm -v "$PWD/out:/test/output" tests
docker compose --env-file .env.default down -v
```

`--env-file .env.default` обязателен, иначе не подставится имя образа: compose
сам подхватывает только файл с именем `.env`. Монтирование в `/test/output`
тоже обязательно, иначе отчёты останутся внутри контейнера.

Без python3 вы получите прогон. С python3 вы получите прогон с отчётами,
проверками и уборкой. На сборочной машине запускается вторым способом.

### Что при этом происходит

```
вы: ./run_local.sh <набор> --repo <ваш репозиторий>
 │
 ├─ 1  читает ваши три файла и проверяет их
 │        ошибка здесь = стоп, контейнеры даже не запускались
 ├─ 2  добавляет к вашему compose свои настройки: лимиты, снятие прав,
 │        отдельную сеть, метку прогона, каталоги /test/input и /test/output
 ├─ 3  поднимает сервисы и ждёт, пока соседи станут готовы (healthcheck)
 ├─ 4  ждёт ваш главный контейнер. Его код возврата и есть вердикт
 ├─ 5  забирает отчёты из /test/output в .tdc-out/reports/<набор>/
 │        делается всегда, и когда прошло, и когда упало
 └─ 6  сносит контейнеры, тома и сеть. На машине не остаётся ничего
```

Ваш `docker-compose.yml` при этом не меняется. Настройки накладываются вторым
файлом поверх, он лежит в `.tdc-out/_work/<набор>/docker-compose.harness.yml`.

Проверить конфигурацию, ничего не запуская:

```sh
./run_local.sh integration --repo <ваш репозиторий> --dry-run
```

Посмотреть весь путь целиком на готовом примере, ничего не настраивая:

```sh
./smoke/demo_from_template.sh
```

Добавьте `.tdc-out/` в `.gitignore`. Каталог пересоздаётся при каждом запуске.

## Если упало

Первым делом откройте `.tdc-out/reports/<набор>/_infra/compose-logs.txt`.
Он пишется всегда, даже когда прогон развалился.

| Сообщение | Что делать |
|---|---|
| `набор ... не найден` | опечатка в имени, ниже напечатан список доступных |
| `permission denied ... docker.sock` | вы не в группе `docker`: `usermod -aG docker $USER` и перезайти |
| `compose.build_forbidden` | уберите `build:`, образ берётся готовым из ProGet |
| `compose.image_tag` | поставьте конкретный тег вместо `latest` |
| `compose.container_name_forbidden`, `compose.restart_forbidden` | уберите эти строки |
| `compose.bind_mount` | уберите проброс папок с хоста, файлы подавайте через `<inputs>` |
| `env.reserved_prefix` | заняты имена на `TEST_`, `BUILD_`, `VCS_`, `COMPOSE_`, `DOCKER_` |
| `reports.zero_matches` | отчёт не попал в `/test/output` либо путь в манифесте не совпал |
| `failed switching to 'postgres'` | базе не хватает прав, см. раздел про базу |
| `No space left on device` | на машине кончилось место, нужно от 5 ГБ |

## Справочно

Переменные внутри контейнера: `TEST_OUTPUT`, `TEST_INPUT`, `TEST_OS`,
`TEST_ARCH`, `TEST_CONFIG_NAME`, `BUILD_NUMBER`, `VCS_REVISION`.

Запрещено в compose: `build:`, проброс папок с хоста, `ports:`,
`container_name`, `restart`, `privileged`, `cap_add`, сеть и PID хоста, образы
не из ProGet, тег `latest`.

База поднимается пустой при каждом запуске. Схему создают сами тесты. Порядок
тестов не гарантирован. Интернета изнутри нет.

Вопросы: `<канал, чат или почта: заполнить>`.
