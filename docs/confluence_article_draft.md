# Интеграционные тесты в Docker: регламент `test_docker_config/`

> **ЧЕРНОВИК статьи для Confluence.** Основание: IN-662 (критерии приёмки,
> пп. 3–5), контракт v1 (`test_cfg_schema_draft.md`). Валидатор и раннер —
> инструментальный репозиторий `tdc-runner`. Перед публикацией: проставить
> ссылки на Jira/Bitbucket, сверить с командой OpenIde.Backend.

---

## 1. Что это и для кого

Регламент описывает, как оформить **компонентные интеграционные тесты**
проекта так, чтобы они автоматически запускались в TeamCity после каждого
коммита и точно так же — локально, в окружении разработчика.

Схема работы:

1. Сборочная конфигурация собирает проект и публикует артефакты.
2. Тестовая конфигурация TeamCity находит в вашем репозитории каталог
   `test_docker_config/`, поднимает описанный вами `docker-compose`,
   подаёт внутрь заявленные входы и забирает отчёты.
3. Те же тесты запускаются на машине разработчика локальным раннером —
   **тем же кодом**, что и в CI.

Для кого: команды, у которых интеграционные тесты запускаются в
docker-контейнерах (пример существующей практики — `Elara.OpenIde.Backend`,
интеграция с PostgreSQL и развёрнутым backend).

Что нужно от команды: три файла в репозитории (см. §2). Всё остальное —
шаблонная конфигурация TeamCity и раннер — уже готово и одинаково для всех.

## 2. Требования к репозиторию

### 2.1. Дерево каталогов

Строго в **корне репозитория**:

```
<repo root>/
  test_docker_config/                  # корень, фиксированное имя
    post_commit/                       # класс триггера «после каждого коммита»
      <имя_конфигурации>/
        docker-compose.yml             # единственный compose-файл
        .env.default                   # обязателен, даже пустой
        test_cfg.xml                   # манифест конфигурации
```

- `post_commit/` — единственный класс триггера в v1. Будущие классы
  (nightly, manual) появятся сиблингами, заранее их не заводить.
- Несколько каталогов `<имя_конфигурации>/` = несколько независимых
  тест-ранов одного билда. Пример миграции OpenIde: два корневых
  compose-файла превращаются в две папки — `postgres_integration/` и
  `backend_integration/`.

### 2.2. Имя конфигурации

Только **строчные** латинские буквы, цифры, подчёркивание: `[a-z0-9_]+`.
Без пробелов, без дефисов, без заглавных.

Почему без заглавных: `Smoke/` и `smoke/` — разные каталоги на Linux, но
склеиваются на case-insensitive ФС (Windows, macOS) и в раскладке отчётов.

### 2.3. Ровно три файла

| Файл | Обязателен | Назначение |
|---|---|---|
| `docker-compose.yml` | да | Описание сервисов. Только это имя. |
| `.env.default` | да (даже пустой) | Значения переменных по умолчанию (§5). |
| `test_cfg.xml` | да | Манифест: где исполнять, что подать, что забрать (§3). |

### 2.4. Запреты

- **Любой другой** `docker-compose*.y*ml` / `compose*.y*ml` в каталоге
  конфигурации запрещён (ошибка `compose.extra_file`). Причина: compose
  молча авто-мёржит `docker-compose.override.yml` мимо валидатора. Раннер
  запускает compose явным списком `-f`, вашим файлом плюс своим override.
- Файл `.env` в каталог **не коммитить** — его генерирует раннер,
  добавьте в `.gitignore`.
- Top-level `name:` в compose-файле не используется: имя проекта задаёт
  раннер через `-p` (иначе параллельные раны конфликтуют).

## 3. `test_cfg.xml`

### 3.1. Минимальный пример

```xml
<?xml version="1.0" encoding="UTF-8"?>
<test_cfg version="1">
  <meta>
    <description>Интеграционные тесты backend против PostgreSQL</description>
  </meta>

  <environment>
    <os>linux</os>
    <arch>x64</arch>
  </environment>

  <inputs/>

  <outputs>
    <report type="tests" format="junit" path="junit/*.xml"/>
  </outputs>

  <execution>
    <main_service>tests</main_service>
    <timeout_minutes>30</timeout_minutes>
  </execution>
</test_cfg>
```

### 3.2. Поля

| Поле | Обяз. | Значения / семантика |
|---|---|---|
| `environment/os` | да | `linux` \| `windows`. Windows — вне скоупа v1: такие конфиги видимо скипаются. |
| `environment/arch` | да | Список через пробел из `x64`, `arm`, `arm64`. Список = матрица: конфиг исполняется каждым совпавшим слотом (§8). |
| `environment/requires/capability` | нет | Имя из закрытого словаря (§3.3). Неизвестное имя — **ошибка валидации**, не skip. |
| `inputs/artifact` | нет | `path` — glob по дереву **опубликованных артефактов** сборки; `dest` — подкаталог в `$TEST_INPUT`. Единственный канал бинарей между сборкой и тестами. Результат глоба дополнительно фильтруется по слоту рана (`slot_filter="off"` — осознанный кросс-слот). |
| `inputs/source` | нет | Исходники из checkout — только явным белым списком. `path` обязан начинаться с литерального подкаталога (`tests/data/**` — можно, `**` в корне — нельзя). |
| `outputs/report` | да, минимум один с `type="tests"` | `type`: `tests` \| `coverage` \| `static_analysis` \| `custom`; `format`: `junit` \| `trx` \| `cobertura` \| `raw`; `path` — glob по `$TEST_OUTPUT`. |
| `outputs/artifact` | нет | Произвольные файлы из `$TEST_OUTPUT` (например, логи) — публикуются как есть. |
| `execution/main_service` | да | Exit code этого сервиса = вердикт рана. Сервис обязан существовать в compose. Обвязка (БД, брокеры) на вердикт не влияет. |
| `execution/timeout_minutes` | да | Целое > 0. Отсчёт от `up`; pull образов — до таймаута и в него не входит. |

Общие правила для `inputs` и `outputs`: glob, совпавший с **0 файлов**, —
провал конфигурации; опт-аут — атрибут `optional="true"`. Пути — без `..`,
без абсолютных.

По умолчанию (`<inputs/>` пуст) в контейнеры **не попадает ничего** —
ни исходники, ни артефакты. Это дефолт контракта, а не ошибка.

### 3.3. Словарь capability (v1)

| Имя | Класс | Отсутствие на агенте |
|---|---|---|
| `docker` | базовая (слот) | провал билда (деградация агента) |
| `docker-compose` | базовая (слот) | провал билда |
| `qemu-user-static` | опциональная (конфиг) | видимый skip конфигурации |

Словарь закрытый и ведётся в этой статье. Нужна новая capability —
заявка через владельцев шаблона.

### 3.4. Типовые ошибки

- Нет ни одного `<report type="tests">` → `outputs.no_tests_report`.
  Отчёт о тестах обязателен всегда.
- `main_service`, которого нет в compose → `compose.main_service`.
- Опечатка в имени capability → `capability.unknown` (ошибка, не skip —
  иначе опечатка молча выключала бы конфиг).
- `<source path="**">` (глоб от корня репо) → `inputs.source_root_glob`.
- `path` с `..` или абсолютный → `inputs.path_escape`.
- Два input'а кладут файл в один и тот же конечный путь →
  `inputs.dest_collision`.

## 4. Правила `docker-compose.yml`

Валидация — **белый список** по нормализованному `docker compose config`
(anchors, `extends`, `${}`-подстановки раскрываются до проверки — «спрятать»
запрещённое поле нельзя). Исполнитель зафиксирован: **Compose v2**, одна
пиновая версия на агентах и в локальном раннере. Ключ `version:` в файле
не пишется.

### 4.1. Что можно

В каждом сервисе разрешены только:

| Поле | Ограничения |
|---|---|
| `image` | обязателен; см. §4.2 |
| `command`, `entrypoint` | — |
| `environment` | — |
| `env_file` | только `./.env` (генерируется раннером) |
| `depends_on` | рекомендуется с `condition: service_healthy` |
| `healthcheck` | — |
| `expose` | внутрипроектная видимость портов (вместо `ports`) |
| `working_dir`, `user` | — |
| `networks` | только внутрипроектные, `internal: true`; без секции — изолированная сеть по умолчанию |
| `volumes` | только **named volumes**, без `driver_opts`/`external`; target вне `/test/**`; не docker.sock |

Всё, чего нет в таблице, — отбраковка на валидации.

### 4.2. Откуда берутся образы

- `image` — полное имя с хостом внутреннего registry:
  `proget.inc.elara.local/...`. Пример (реальный, из OpenIde):
  `proget.inc.elara.local/main/library/postgres:18.1`.
- Тег обязателен и **иммутабелен**: `:latest` и «без тега» — отбраковка.
  Пин по digest — рекомендуется.
- Агенты закрытой сети: docker.io и прочие внешние registry недоступны
  в принципе. Нужен внешний образ — заводится зеркало в ProGet.
- Свои тест-образы собирает и публикует **сборочная** конфигурация
  (или тесты подаются бинарями в `$TEST_INPUT` на готовый runtime-образ).

### 4.3. Почему запрещено (главное)

| Поле | Почему |
|---|---|
| `build:` | Исходники уезжают в образ через COPY — обход правила «в контейнеры не попадает ничего лишнего»; плюс на офлайн-агентах сборка образов не работает. Собирайте образы в сборочной конфигурации. |
| bind-mounts, `volumes_from` | Прямой доступ к ФС агента. Входы монтирует раннер (`$TEST_INPUT` read-only), руками — нельзя. |
| `/var/run/docker.sock` | Эквивалент root на хосте-агенте. Обвязку (БД, брокеры) поднимает compose, а не тест-код изнутри контейнера. |
| `container_name:` | Фиксированное имя ломает параллельные раны на одном агенте. Имена генерирует compose из project name. |
| `restart:` | Контейнер переживает ран и остаётся висеть на агенте. На `main_service` ещё и ломает вердикт. |
| `ports:` | Host-биндинг — конфликты портов между параллельными ранами. Внутри проекта сервисы видят друг друга по именам; наружу порты не нужны. |
| `privileged`, `cap_add`, `devices`, `security_opt`, `sysctls`, `*_mode: host`, `userns_mode`, `cgroup_parent` | Эскалация привилегий / выход из изоляции. Раннер сам принудительно ставит `cap_drop: [ALL]` и `no-new-privileges`. |
| `extends` с внешним `file:`, `secrets`/`configs` с `file:`, `logging` с address, `dns`/`extra_hosts` | Чтение чужих файлов, увод логов и трафика наружу. |

Раннер добавляет своим override-файлом: тома input/output, инжект
переменных (§5), лимиты (`pids_limit` 512, память 2g, cpus 2 — значения
уточняются), метку `tc.in662` для уборки сирот. Задать resources в своём
файле нельзя — мёрж лимитов аддитивен, перекрытием не спасёшься, поэтому
это тоже отбраковка.

## 5. Переменные окружения

### 5.1. `.env.default`

- Обязателен, даже пустой. Формат — строки `KEY=value`, `#` — комментарий.
- Это **значения по умолчанию для локального запуска** и документация
  «что вообще настраивается» (аналог `.env.example` у OpenIde).
- Раннер генерирует из него рабочий `.env` (CI-переменные поверх) —
  `.env` в `.gitignore`, руками не создавать.

### 5.2. Что инжектирует CI

В environment **каждого** сервиса раннер добавляет фиксированный список —
и ничего сверх него:

| Переменная | Значение |
|---|---|
| `TEST_INPUT` | путь к входам внутри контейнера (`/test/input`, read-only) |
| `TEST_OUTPUT` | путь для отчётов (`/test/output`, read-write) |
| `TEST_OS` | ОС слота: `lin` \| `win` |
| `TEST_ARCH` | архитектура слота: `x64` \| `arm` \| `arm64` |
| `TEST_CONFIG_NAME` | имя каталога конфигурации |
| `BUILD_NUMBER` | номер билда TeamCity (`local` при локальном запуске) |
| `VCS_REVISION` | ревизия checkout |

В путях используйте переменные, не литералы `/test/...` — задел под
windows-слот.

Секреты (password-параметры TeamCity, креды ProGet) в контейнеры **не
попадают в принципе**: `$TEST_OUTPUT` публикуется артефактом билда — это
готовый канал утечки.

### 5.3. Приоритет и reserved-префиксы

- Приоритет: **CI-переменные всегда перекрывают** `.env.default`
  (согласуется с практикой OpenIde: `.runsettings` > ОС > `.env`).
- В `.env.default` **запрещены** имена с префиксами `COMPOSE_*`,
  `DOCKER_*`, `TEST_*`, `BUILD_*`, `VCS_*` (ошибка `env.reserved_name`) —
  иначе можно подменить project name, демона или пути монтирования.

## 6. Выходные артефакты

### 6.1. Куда писать

Тесты пишут **только в `$TEST_OUTPUT`**. Всё остальное внутри контейнера
после `down -v` исчезает.

### 6.2. Раскладка отчётов

После рана раннер раскладывает содержимое по регламенту:

```
reports/
  <имя_конфигурации>/
    tests/            # junit/trx по глобам из test_cfg.xml
    coverage/         # cobertura + HTML-отчёт
    static_analysis/  # прочие типизированные отчёты
    custom/           # артефакты «как есть»
    _infra/           # служебная диагностика — пишет раннер, не вы
```

`_infra/` заполняется **всегда, до** `down`: `docker compose logs`,
`compose ps -a`, при таймауте — `docker inspect` main_service. Это улики
для разбора падений; каталог зарезервирован, самим туда не писать.

### 6.3. Форматы

| format | Что с ним происходит |
|---|---|
| `junit` | **Обязательный минимум** для `type="tests"`. Импортируется в TeamCity — тесты видны поимённо во вкладке Tests. |
| `trx` | dotnet-отчёты (`dotnet test`); импортируются как mstest / конвертируются в junit. Для OpenIde — штатный путь. |
| `cobertura` | Нативного импорта покрытия в TeamCity 2018.1 нет: числа уходят в статистику билда (`buildStatisticValue`), а **HTML-отчёт генерируется внутри тест-контейнера** (инструменты — в образе, не на агенте) и публикуется артефактом. |
| `raw` | Публикация как есть, без обработки. |

## 7. Локальный запуск

Локальный раннер — часть контракта: он гоняет **те же шаги тем же кодом**,
что CI (валидация → staging → генерация `.env` и override → run → сбор
отчётов → уборка).

```
# проверить конфигурации без запуска docker-рана
python3 -m tdc validate --repo <путь к репо>

# прогнать одну конфигурацию локально
python3 -m tdc run --repo <путь к репо> --slot lin-x64 --mode local \
    --config <имя_конфигурации> --out <каталог результатов> \
    [--artifacts <каталог с артефактами сборки>]
```

- `--artifacts` — локальная папка, играющая роль дерева опубликованных
  артефактов (скачайте их из TeamCity или соберите локально).
- Результаты — в `<каталог результатов>/reports/<имя>/...`, ровно как в CI.
- `--dry-run` — валидация + staging + генерация без обращений к docker.

**Не запускайте** голый `docker compose up` в каталоге конфигурации: он
ведёт себя иначе (compose читает только файл с именем `.env`,
`/test/input` не смонтирован, лимиты и инжект переменных отсутствуют) —
«у меня локально работало» с таким запуском не считается.

Разовая настройка машины разработчика: Docker + Compose v2 (пин той же
версии, раздача через ProGet) и обязательная правка подсетей в daemon.json
(`bip` + `default-address-pools`) — дефолтные docker-подсети
172.16–17.0.0/16 пересекаются с офисной сетью. Пример конфигурации — в
инструкции OpenIde «Запуск интеграционных тестов в Docker».

## 8. Матчинг ОС/архитектуры и слоты

- Тестовые конфигурации TeamCity — фиксированные **слоты**: `lin-x64`,
  `lin-arm`, `lin-arm64` (windows — вне скоупа v1). Каждый слот сам
  сканирует `post_commit/*/test_cfg.xml` и последовательно гоняет конфиги,
  чей `<os>`/`<arch>` совпал.
- Словарь осей — легаси-ось слотов, та же, что в именах `.nupkg`:
  `lin`/`win` × `x64`/`arm`/`arm64`. Второго словаря нет.
- `<arch>x64 arm64</arch>` = конфиг исполнится и слотом `lin-x64`, и
  `lin-arm64`. Compose при этом пишется **один раз**: арх приходит
  переменной `TEST_ARCH` (`image: proget.inc.elara.local/foo:1.2-${TEST_ARCH}`).
- Артефакты по `inputs/artifact` фильтруются по слоту: токены `lin`/`win`
  и `x64`/`arm`/`arm64` в пути/имени файла (как в именах nupkg) должны
  совпасть со слотом рана; `arm` ≠ `arm64`. Файл без слот-токенов
  (общие тестовые данные) проходит в любой слот. Отключение —
  `slot_filter="off"`, только осознанно.
- Слот без единого совпавшего конфига — зелёный билд с пометкой
  «no test configs for slot».

## 9. FAQ и типовые отказы валидатора

### 9.1. Частые вопросы

**Валидатор отверг `docker-compose.override.yml`, он же мой, локальный.**
Убрать из каталога (и из репо). Любой второй compose-файл запрещён —
compose подхватывает override молча, мимо валидации. Локальные отличия —
через переменные в `.env.default`.

**Как тестам получить бинари свежей сборки?**
Только через опубликованные артефакты: `<artifact path="..."/>` →
файлы появятся в `$TEST_INPUT`. Прямого канала «build-выхлоп → тест» нет.

**Почему тесты не видят исходники репозитория?**
По умолчанию так и должно быть. Нужны данные — явный
`<source path="tests/data/**" dest="data/"/>`.

**Куда делись контейнеры после падения теста?**
`down -v` выполняется всегда. Логи и `ps -a` уже собраны в
`reports/<имя>/_infra/` — начинайте разбор оттуда.

**Тест прошёл локально, упал в CI на arm64.**
Проверьте, что образы всех сервисов существуют для arm64
(`docker manifest inspect`), и что артефакты не отфильтровались по слоту
(warning `inputs.slot_filtered` в логе рана).

**Нужен Testcontainers / docker.sock изнутри теста.**
Запрещено. Обвязку поднимает compose (сервисы + `depends_on` +
`healthcheck`), тест-код к докеру не обращается.

### 9.2. Коды ошибок

Структура и файлы:

| Код | Причина / что делать |
|---|---|
| `config.bad_name` | Имя каталога не `[a-z0-9_]+`. Переименовать. |
| `config.missing_file` | Нет одного из трёх обязательных файлов. |
| `compose.extra_file` | Лишний `*compose*.y*ml` в каталоге. Удалить. |

`test_cfg.xml`:

| Код | Причина / что делать |
|---|---|
| `outputs.no_tests_report` | Нет `<report type="tests">`. Добавить junit-отчёт. |
| `capability.unknown` | Имя вне словаря §3.3. Опечатка или заявка на новую capability. |
| `inputs.path_escape` | `..` или абсолютный путь в `path`/`dest`. |
| `inputs.source_root_glob` | `<source>` глобится от корня репо. Начните с подкаталога. |

| `inputs.slot_filtered` | (warning) Часть файлов отфильтрована по слоту — норма для матрицы, но проверьте при «пустом» `$TEST_INPUT`. |

## Приложение А. Чек-лист заведения конфигурации

1. Создать `test_docker_config/post_commit/<имя>/` (имя — `[a-z0-9_]+`).
2. Написать `docker-compose.yml` в рамках белого списка §4;
   образы — из ProGet, с иммутабельными тегами.
3. Заполнить `.env.default` (без reserved-префиксов), добавить `.env`
   в `.gitignore`.
4. Написать `test_cfg.xml`: os/arch, входы, минимум один
   `<report type="tests" format="junit">`, `main_service`, таймаут.
5. Убедиться, что тесты пишут отчёты в `$TEST_OUTPUT` (пути — через
   переменную).
6. `python3 -m tdc validate --repo .` — до зелёного.
7. Локальный прогон `--mode local` (§7) — до зелёного.
8. Коммит. Проверить ран в тестовой конфигурации TeamCity своего слота.
