# Материал для разговора с разработчиками

Три части: что говорить, тонкости запуска, как писать тесты под эту систему.
В конце сценарий показа на живой машине.

---

# Часть 1. Что говорить

Пять минут. Порядок важен: сначала их боль, потом решение, потом одна команда.

## 1. Начните с того, что у них есть сейчас

> Сегодня интеграционные тесты запускаются руками. Надо поставить Docker,
> скопировать `.env`, вспомнить команду. На выходе только «упало или не
> упало». Кто именно упал, вы не знаете: отчёт остаётся внутри контейнера и
> пропадает вместе с ним. В CI это не запускается вообще.

Это правда для большинства команд, поэтому спорить не будут.

## 2. Скажите, что меняется

> Вы кладёте в репозиторий три файла. В них написано, что нужно вашим тестам:
> какие сервисы рядом, какие файлы, сколько ждать. Дальше запуск, сбор
> результатов и уборка происходят сами. Код тестов не трогаем.

## 3. Покажите картинку

`docs/in662_howto_overview.png`. Скажите одну фразу:

> Сверху то, что делаете вы, и только один раз. Снизу то, что дальше
> происходит само при каждом запуске.

Больше про устройство не рассказывайте.

## 4. Покажите живой пример

`docs/case_dotnet_openide.md`. У коллег было вот так, стало вот так, изменение
это три файла и ноль правок в тестах. Живой пример убеждает лучше объяснений.

## 5. Дайте одну команду

```sh
./run_local.sh <имя набора> --repo <ваш репозиторий>
```

> Это тот же код, который потом запустит сервер. Прошло у вас, пройдёт и там.

Дальше дайте ссылку на [шпаргалку](cheatsheet.md) и заканчивайте. Остальное они
найдут сами, когда упрутся.

## Чего не говорить

Не рассказывайте про слои, изоляцию, права контейнеров и белые списки. Пока
человек не упёрся, ему это не нужно. А когда упрётся, он увидит конкретную
ошибку с готовым ответом в таблице.

## Ответы на три вопроса, которые зададут

**«Придётся переписывать тесты?»**
Нет. Но два места в их настройках, возможно, поправить придётся: адрес базы и
путь, куда пишутся отчёты. См. часть 3.

**«А если у меня не postgres, а <что-то ещё>?»**
Всё равно работает. Система не знает, что за сервисы вы поднимаете. Она знает
только про три файла и docker.

**«Сколько это займёт?»**
Первый набор около двадцати минут, если образ с тестами уже есть. Второй набор
пять минут.

# Часть 2. Тонкости запуска

## Разработчик запускает одной командой

```sh
cd tdc-runner
./run_local.sh <имя набора> --repo <ваш репозиторий>
```

Никаких `docker compose up` руками. Система добавляет к вашему файлу
ограничения, изоляцию и уборку. Запущенное вручную не уберётся за собой.

## Права на docker

Если пользователь не в группе `docker`, будет ошибка
`permission denied ... /var/run/docker.sock`. Два выхода: запускать через
`sudo` или один раз выполнить `sudo usermod -aG docker $USER` и
перелогиниться. На агенте сборки служебный пользователь должен быть в этой
группе.

## Где отчёты

По умолчанию в `.tdc-out/` внутри тестируемого репозитория. Каталог надо
добавить в `.gitignore`. Другое место задаётся ключом `--out`.

Каталог полностью пересоздаётся при каждом запуске. Правки внутри пропадут.
Раньше он не чистился, и цифры покрытия складывались между прогонами.

## Проверка без запуска

```sh
python3 -m tdc validate --repo <ваш репозиторий>
```

Секунда, контейнеры не поднимаются. Проверяет три файла и compose по белому
списку. Удобно гонять после каждой правки.

Полная подготовка без контейнеров:

```sh
./run_local.sh <набор> --repo <репо> --dry-run
```

Так проверяется всё, кроме самого запуска: разбор манифеста, подготовка
входных файлов, генерация ограничений.

## Несколько наборов

Каждый набор это отдельная папка внутри `post_commit/`. Локально запускается по
имени, по одному. На сервере запускаются все, которые подходят слоту.

## Ключи, которые нужны не всем

| Ключ | Когда |
|---|---|
| `--artifacts <каталог>` | в манифесте есть `<inputs>` с `<artifact>` |
| `--secrets <каталог>` | в манифесте есть `<secrets>` |
| `--out <каталог>` | отчёты нужны не в `.tdc-out` |
| `--dry-run` | проверить подготовку, не запуская контейнеры |

## Как это поедет в TeamCity

Другой пускалкой, `ci/run_tests.sh`. Она берёт параметры из переменных
окружения, прогоняет все наборы репозитория, подходящие слоту, и делает
предполётную проверку: python, docker, compose, свободное место. Разработчику
знать про неё не обязательно.

Посмотреть, как это выглядит, можно и на своей машине:

```sh
./smoke/run_as_ci.sh <путь к репозиторию>
```

# Часть 3. Как писать тесты под эту систему

Ничего необычного. Но пять правил надо знать заранее, иначе тесты будут
работать локально и падать в контейнере.

## 1. Отчёты пишите в `/test/output`

Только этот каталог переживает контейнер. Всё остальное пропадает.

Для .NET это делают ключи в команде запуска, они уже есть в шаблоне:

```
--logger "trx;LogFileName=integration.trx"
--collect:"XPlat Code Coverage"
--results-directory /test/output/results
```

Для gtest:

```
--gtest_output=xml:/test/output/results/gtest.xml
```

Если ваши тесты сами куда-то пишут диагностику, направьте её туда же. Путь
доступен в переменной `TEST_OUTPUT`.

## 2. Адреса сервисов берите из переменных, а не из кода

Внутри контейнера соседний сервис доступен по имени из compose, а не по
`localhost`. Хост передаётся переменной окружения. В коде тестов не должно
быть зашитого `localhost` или `127.0.0.1`.

Так обычно и сделано. Проблема появляется, когда значение по умолчанию
прописано в конфиге тестов и указывает на `localhost`. Проверьте, что
переменная окружения перекрывает это значение.

## 3. Тесты сами готовят состояние

База поднимается пустой при каждом запуске. Тома сносятся после прогона.
Значит:

- схему создают сами тесты, миграциями или скриптом на старте;
- нельзя рассчитывать на данные от предыдущего прогона;
- тесты должны проходить в любом порядке и на чистой базе.

Это обычно и так выполнено, но проверьте: если у вас есть тест, который
работает только вторым по счёту, он упадёт.

## 4. Тесты не создают контейнеры сами

Testcontainers и прямые вызовы Docker API не поддерживаются. Созданные так
контейнеры не принадлежат прогону: их не убирает ни система, ни уборка по
метке, они остаются на машине навсегда.

Если у вас так сделано, приходите. Решаем отдельно, вариант есть.

## 5. Помечайте интеграционные тесты

Команда запуска отбирает тесты фильтром. Для .NET это атрибуты вроде
`[Trait("Category", "Integration")]`, для gtest суффиксы в именах. Без пометки
в набор попадут все тесты подряд, включая юнитовые.

## Ещё три мелочи

**Наружу в интернет из контейнера хода нет.** Сеть закрытая. Если тест ходит в
интернет, он упадёт. Внешние сервисы поднимайте соседним контейнером и
подменяйте адрес переменной.

**Порты наружу не публикуются.** Внутри сети compose сервисы видят друг друга
по любым портам. Наружу ничего не выставляется, поэтому конфликтов между
параллельными запусками нет.

**Есть таймаут.** По умолчанию столько минут, сколько написано в
`<timeout_minutes>`. Тесты идут дольше: увеличьте значение. Зависли: прогон
будет остановлен, и это правильно.

## Переменные, доступные тестам всегда

| Переменная | Что |
|---|---|
| `TEST_OUTPUT` | куда писать отчёты |
| `TEST_INPUT` | где лежат поданные файлы |
| `TEST_OS`, `TEST_ARCH` | на каком слоте идёт прогон |
| `TEST_CONFIG_NAME` | имя набора |
| `BUILD_NUMBER`, `VCS_REVISION` | откуда собрано |

# Часть 4. Показ на живой машине

Десять минут. Порядок подобран так, чтобы каждый шаг отвечал на вопрос,
который в этот момент возникает.

## Подготовка до показа

```sh
cd ~/tdc-runner
git pull
python3 -m unittest discover -s tests    # убедиться, что всё зелёное
```

Убедитесь, что docker поднят и на диске есть место.

## Шаг 1. Показать, что добавляется в репозиторий

```sh
find ~/elara_openide_backend/test_docker_config -type f
```

Три файла. Скажите: «это всё, что появилось в репозитории».

Откройте `docker-compose.yml` и покажите два места: строку `image` и три
последних ключа в `command`. Скажите: «вот эти три ключа и есть всё, ради чего
затевалось. Без них отчёты остаются внутри контейнера».

## Шаг 2. Проверка за секунду

```sh
python3 -m tdc validate --repo ~/elara_openide_backend
```

Показывает `OK`. Скажите: «контейнеры не поднимались, проверились файлы».

## Шаг 3. Показать, что защита работает

Это самый убедительный шаг. Временно сломайте профиль:

```sh
cd ~/elara_openide_backend/test_docker_config/post_commit/postgres_integration
cp docker-compose.yml /tmp/backup.yml
sed -i 's|    image: |    container_name: fixed-name\n    image: |' docker-compose.yml
cd ~/tdc-runner && python3 -m tdc validate --repo ~/elara_openide_backend
```

Валидатор скажет `compose.container_name_forbidden` и объяснит, почему.
Верните файл:

```sh
cp /tmp/backup.yml ~/elara_openide_backend/test_docker_config/post_commit/postgres_integration/docker-compose.yml
```

Скажите: «ошибку в конфигурации видно за секунду, до того как что-то
запустилось».

## Шаг 4. Настоящий прогон

```sh
sudo ./run_local.sh postgres_integration --repo ~/elara_openide_backend
```

Показывайте вывод по мере появления. Обратите внимание на строки:

- `importData type='mstest'` это отчёт, который подхватит TeamCity;
- `buildStatisticValue CodeCoverage...` это цифры покрытия;
- `passed (main service exit code 0)`.

## Шаг 5. Что осталось на диске

```sh
find ~/elara_openide_backend/.tdc-out/reports -type f | head
```

Покажите три вещи: `tests/` с отчётом, `coverage/` с покрытием, `_infra/` с
логами контейнеров.

Сколько тестов реально прошло:

```sh
python3 -c "
from xml.etree import ElementTree as ET; import glob
ns={'t':'http://microsoft.com/schemas/VisualStudio/TeamTest/2010'}
f=glob.glob('$HOME/elara_openide_backend/.tdc-out/reports/**/*.trx',recursive=True)[0]
print(dict(ET.parse(f).getroot().find('.//t:Counters',ns).attrib))"
```

## Шаг 6. Машина чистая

```sh
docker ps -aq --filter label=tc.in662 | wc -l
docker volume ls -q --filter label=tc.in662 | wc -l
```

Оба нуля. Скажите: «после прогона на машине не остаётся ничего. Это важно для
общего агента: один забытый том ломает следующую сборку».

## Шаг 7. Как это поедет в TeamCity

```sh
sudo ./smoke/run_as_ci.sh ~/elara_openide_backend
```

Скажите: «то же самое, но параметры приходят из переменных сборки, и
прогоняются все наборы репозитория, а не один».

## Если во время показа что-то упадёт

Это нормально и даже полезно. Откройте
`.tdc-out/reports/<набор>/_infra/compose-logs.txt` и покажите, что причина
видна сразу. Скажите: «этот файл пишется всегда, даже когда прогон
развалился».
