# Как подключить свои интеграционные тесты

Для разработчика компонента. Один маршрут сверху вниз, минут на двадцать.
Код тестов менять не нужно.

![Как это работает целиком](in662_howto_overview.png)

Верхняя дорожка — то, что делаете вы, и только один раз. Нижняя — то, что
происходит само при каждом прогоне. Если картинки достаточно, дальше можно
читать по диагонали.

---

## 1. Подходит ли это вам сейчас

| Условие | Сейчас |
|---|---|
| ОС и архитектура | только Linux x64 |
| Когда запускать | после коммита |
| Тесты внутри контейнера | да |
| Тесты сами создают контейнеры через Docker API | **не поддерживается**, приходите отдельно |
| Windows | второй этап |

Если ваш случай не подходит — напишите, посмотрим вместе.

## 2. Что понадобится

На вашей машине: **docker**, **python3**. Больше ничего ставить не нужно —
compose едет внутри инструмента.

Сам инструмент — отдельный репозиторий, склонировать один раз рядом с вашим:

```sh
git clone https://github.com/npushkarev/tdc-runner.git
```

Дальше все команды с `python3 -m tdc` и `./run_local.sh` выполняются **из
каталога `tdc-runner`**, а путь к вашему репозиторию передаётся параметром.

Ещё нужен **образ с вашими собранными тестами в ProGet**. Кто его собирает и в
какой фид кладёт — согласуйте отдельно (это открытый пункт, см. конец файла).

## 3. Быстрый старт

**Скопируйте шаблон** в корень своего репозитория:

```sh
# для .NET
cp -r tdc-runner/templates/dotnet/test_docker_config <ваш репозиторий>/
# для C++
cp -r tdc-runner/templates/cpp/test_docker_config <ваш репозиторий>/
```

Получится:

```
<ваш репозиторий>/test_docker_config/post_commit/integration/
    docker-compose.yml
    .env.default
    test_cfg.xml
```

Папку `integration` можно переименовать — маленькими буквами, цифры и
подчёркивание. Наборов может быть несколько, каждый в своей папке.

**Замените в шаблоне помеченное** словом `ЗАМЕНИТЬ`. Их немного:

| Где | Что подставить |
|---|---|
| `docker-compose.yml`, `image:` | имя вашего образа в ProGet и конкретный тег |
| `docker-compose.yml`, `command:` | путь к тест-проекту (.NET) или имя бинарника (C++) |
| `docker-compose.yml`, `--filter` | как у вас помечены интеграционные тесты (.NET) |
| `test_cfg.xml`, `<description>` | одна строка, что это за набор |
| `test_cfg.xml`, `<timeout_minutes>` | если тесты идут дольше |
| `test_cfg.xml`, `<inputs>` | какие файлы сборки положить внутрь (C++) |

Всё остальное в шаблоне — рабочее, менять не надо.

**Проверьте** (быстро, контейнеры не поднимаются):

```sh
cd tdc-runner
python3 -m tdc validate --repo <ваш репозиторий>
```

Должно быть `OK`. Если нет — смотрите раздел «Если не работает».

**Прогоните целиком:**

```sh
# .NET: всё нужное уже внутри образа с тестами
./run_local.sh integration --repo <ваш репозиторий>

# C++: бинарники приезжают снаружи, поэтому нужен каталог со сборкой
./run_local.sh integration --repo <ваш репозиторий> --artifacts <каталог со сборкой>
```

Отчёты лягут в `.tdc-out/` внутри вашего репозитория — **добавьте его в
`.gitignore`**, коммитить его не нужно. Другое место — ключ `--out`.

**Успех выглядит так:** код возврата 0, и в каталоге отчётов появилось:

```
reports/integration/tests/…      результаты тестов
reports/integration/coverage/…   покрытие, если собираете
reports/integration/_infra/…     логи контейнеров
```

**Закоммитьте** три файла. Дальше их подхватит TeamCity.

---

## 4. Два правила, которые важнее остальных

**Отчёты пишите в `/test/output`.** Это единственный каталог, который переживёт
контейнер. Всё, что тесты положат в другое место, исчезнет. В шаблонах ключи
для этого уже проставлены.

**Сервисы видят друг друга по имени из compose**, а не по `localhost`. Если
рядом база с именем `postgres`, то хост для подключения — `postgres`.

---

## 5. Если не работает

Сначала посмотрите `reports/<набор>/_infra/compose-logs.txt` — там вывод всех
контейнеров, он сохраняется даже когда прогон развалился.

| Сообщение | Что делать |
|---|---|
| `compose.build_forbidden` | убрать `build:`: образ собирается отдельно и берётся из ProGet |
| `compose.image_tag` | поставить конкретный тег вместо `latest` или его отсутствия |
| `compose.image_registry` | образ должен быть из ProGet |
| `compose.container_name_forbidden`, `compose.restart_forbidden` | убрать эти строки, имена и перезапуск задаёт система |
| `compose.bind_mount` | убрать проброс папок с хоста, файлы подавать через `<inputs>` |
| `env.reserved_prefix` | переименовать переменную: `TEST_*`, `BUILD_*`, `VCS_*`, `COMPOSE_*`, `DOCKER_*` заняты |
| `reports.zero_matches` | отчёт не найден: проверьте, что тесты пишут в `/test/output`, и что путь в `test_cfg.xml` совпадает |
| `up failed …` | контейнер не поднялся, причина в `_infra/compose-logs.txt` |
| `failed switching to 'postgres'` | базе не хватает прав, см. рецепт «база рядом» |
| `No space left on device` | кончилось место на диске машины |

## 6. Рецепты

### База данных рядом с тестами

Добавьте сервис и дождитесь его готовности:

```yaml
  tests:
    depends_on:
      postgres:
        condition: service_healthy
    environment:
      - POSTGRES_HOST=postgres
      - POSTGRES_PORT=5432
      - POSTGRES_USER
      - POSTGRES_PASSWORD

  postgres:
    image: proget.inc.elara.local/FEED/postgres:18.1
    environment:
      - POSTGRES_USER
      - POSTGRES_PASSWORD
    healthcheck:
      test: ["CMD", "pg_isready", "-U", "${POSTGRES_USER}", "-d", "postgres"]
      interval: 5s
      timeout: 3s
      retries: 5
      start_period: 10s
```

В `.env.default`:

```
POSTGRES_USER=test
POSTGRES_PASSWORD=test
```

И **обязательно** в `test_cfg.xml` — иначе база не стартует, она создаёт свой
каталог данных при первом запуске:

```xml
  <privileges>
    <service name="postgres" cap_add="CHOWN DAC_OVERRIDE FOWNER SETGID SETUID"/>
  </privileges>
```

### Пароли — механизм ещё не реализован

По замыслу пароли будут приезжать файлами в `/test/secrets`, минуя переменные
окружения, git и отчёты. **Пока этого нет:** блок `<secrets>` в `test_cfg.xml`
вызовет ошибку валидации, и это сделано намеренно — чтобы никто не решил, что
пароль доставлен, и не получил пустое место вместо значения.

Тестовые заглушки вроде `POSTGRES_PASSWORD=test`, которые не дают доступа никуда
за пределы прогона, можно держать в `.env.default`. Настоящий секрет — приходите,
подберём обходной путь под ваш случай.

### Локальные значения, которые не хочется коммитить

Положите рядом `.env.local` — он перекрывает `.env.default`, но читается
**только при локальном запуске**. Добавьте его в `.gitignore`: если он всё же
попадёт в репозиторий, на сервере он будет проигнорирован с предупреждением
в логе — прогон не должен зависеть от чьей-то машины.

## 7. Справочник

**Каталоги внутри контейнера**

| Путь | Что это |
|---|---|
| `/test/output` | сюда пишем отчёты, отсюда их забирают |
| `/test/input` | то, что перечислено в `<inputs>`, только чтение |
| `/test/secrets` | пароли файлами — **механизм ещё не реализован** |

Пути в `<outputs>` считаются **от `/test/output`**, в `<inputs>` `dest` —
**от `/test/input`**.

**Переменные, доступные всегда:** `TEST_INPUT`, `TEST_OUTPUT`, `TEST_OS`,
`TEST_ARCH`, `TEST_CONFIG_NAME`, `BUILD_NUMBER`, `VCS_REVISION`.

**Форматы отчётов:** `trx` (.NET), `junit` (gtest и другие), `cobertura`
(покрытие), `raw` (просто файл). Незнакомый тип отчёта не ломает прогон — он
просто сохраняется как есть.

**Что в compose запрещено:** `build:`, проброс папок с хоста, `ports:`,
`container_name`, `restart`, `privileged`, `cap_add`, сеть и PID хоста,
образы не из ProGet и теги `latest`.

## 8. Что ещё не решено

Честно, чтобы не было сюрпризов:

- **какая конфигурация в TeamCity** будет запускать наборы и по какому триггеру —
  решает лид;
- **в какой фид ProGet** класть образы с тестами и кто их собирает — согласуется;
- **arm-слоты** — механика готова, нужны образы под эти архитектуры;
- **Windows** — второй этап.

Вопросы и случаи, которые не ложатся в шаблон, — ко мне.
