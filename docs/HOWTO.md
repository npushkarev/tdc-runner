# Как подключить свои интеграционные тесты

Инструкция для разработчика. Занимает минут двадцать. Код тестов менять не нужно.

![Как это работает целиком](in662_howto_overview.png)

Сверху то, что делаете вы. Один раз. Снизу то, что дальше происходит само.

Хотите сначала посмотреть на живой пример: [разбор проекта OpenIde](case_dotnet_openide.md).

---

## 1. Подходит ли вам это сейчас

| Что | Ответ |
|---|---|
| ОС и архитектура контейнеров | только Linux x64 |
| Когда запускается | после коммита |
| Тесты работают внутри контейнера | да |
| Тесты сами создают контейнеры через Docker API | нет, пока не поддерживается |
| Windows | будет на втором этапе |

Локально запускать можно с любой машины, где есть docker.

Ваш случай не подошёл: `<канал, чат или почта: заполнить>`.

## 2. Что нужно заранее

На вашей машине: `docker` и `python3`. Больше ничего ставить не надо.

Скачайте инструмент один раз:

```sh
git clone <адрес репозитория tdc-runner>
```

Все команды ниже запускаются из каталога `tdc-runner`. Путь к своему
репозиторию вы передаёте параметром.

Ещё нужен образ с вашими собранными тестами в ProGet. Кто его собирает и в
какой фид кладёт, согласуйте отдельно. Это пока решается индивидуально.

## 3. Скопируйте шаблон

Из каталога `tdc-runner`:

```sh
# для .NET
cp -r templates/dotnet/test_docker_config <ваш репозиторий>/

# для C++
cp -r templates/cpp/test_docker_config <ваш репозиторий>/
```

Получится:

```
<ваш репозиторий>/test_docker_config/post_commit/integration/
    docker-compose.yml
    .env.default
    test_cfg.xml
```

Папку `integration` можно переименовать. Разрешены маленькие латинские буквы,
цифры, подчёркивание. Наборов может быть несколько. Каждый лежит в своей папке
и запускается отдельно.

## 4. Замените помеченное

В шаблоне помечено словом `ЗАМЕНИТЬ`. Таких мест немного:

| Файл | Что подставить |
|---|---|
| `docker-compose.yml`, `image:` | имя вашего образа в ProGet и конкретный тег |
| `docker-compose.yml`, `command:` | путь к тест-проекту для .NET, имя бинарника для C++ |
| `docker-compose.yml`, `--filter` | как у вас помечены интеграционные тесты (.NET) |
| `test_cfg.xml`, `<description>` | одна строка про этот набор |
| `test_cfg.xml`, `<timeout_minutes>` | если тесты идут дольше 20 минут |
| `test_cfg.xml`, `<inputs>` | какие файлы сборки положить внутрь (C++) |

Остальное в шаблоне рабочее. Менять не надо.

## 5. Проверьте у себя

Быстрая проверка файлов. Контейнеры не поднимаются:

```sh
cd tdc-runner
python3 -m tdc validate --repo <ваш репозиторий>
```

Полный прогон:

```sh
# .NET: всё нужное уже внутри образа с тестами
./run_local.sh integration --repo <ваш репозиторий>

# C++: бинарники приезжают снаружи, поэтому нужен каталог со сборкой
./run_local.sh integration --repo <ваш репозиторий> --artifacts <каталог со сборкой>
```

Отчёты появятся в `.tdc-out/` внутри вашего репозитория. Добавьте этот каталог
в `.gitignore`. Другое место задаётся ключом `--out`.

Прогон удался, если команда завершилась без ошибок и появились файлы:

```
<ваш репозиторий>/.tdc-out/reports/integration/tests/…      результаты тестов
<ваш репозиторий>/.tdc-out/reports/integration/coverage/…   покрытие, если собираете
<ваш репозиторий>/.tdc-out/reports/integration/_infra/…     логи контейнеров
```

## 6. Закоммитьте три файла

На этом ваша часть закончена. Автоматический запуск в TeamCity сейчас
настраивается. Пока набор запускается вручную командой из шага 5.

---

## Два правила, из-за которых чаще всего не работает

**Отчёты пишите в `/test/output`.** Только этот каталог переживёт контейнер.
Файлы в других местах пропадут. В шаблонах нужные ключи уже стоят.

**К соседним сервисам обращайтесь по имени из compose.** Не по `localhost`.
Если рядом база с именем `postgres`, то хост подключения будет `postgres`.

---

## Если не работает

Сначала откройте `.tdc-out/reports/<набор>/_infra/compose-logs.txt`. Там вывод всех
контейнеров. Файл сохраняется всегда, даже когда прогон упал.

| Сообщение | Что делать |
|---|---|
| `compose.build_forbidden` | уберите `build:`. Образ собирается отдельно и берётся из ProGet |
| `compose.image_tag` | поставьте конкретный тег вместо `latest` или пустого |
| `compose.image_registry` | образ должен быть из ProGet |
| `compose.container_name_forbidden` | уберите `container_name`, имена задаёт система |
| `compose.restart_forbidden` | уберите `restart` |
| `compose.bind_mount` | уберите проброс папок с хоста. Файлы подавайте через `<inputs>` |
| `env.reserved_prefix` | переименуйте переменную. Заняты `TEST_*`, `BUILD_*`, `VCS_*`, `COMPOSE_*`, `DOCKER_*` |
| `reports.zero_matches` | отчёт не найден. Проверьте, что тесты пишут в `/test/output` и что путь в `test_cfg.xml` совпадает |
| `secrets.file_missing` | секрет объявлен, но файла нет. См. раздел про пароли |
| `up failed …` | контейнер не поднялся. Причина в `_infra/compose-logs.txt` |
| `failed switching to 'postgres'` | базе не хватает прав. См. рецепт про базу |
| `No space left on device` | на машине кончилось место |

## Рецепты

### База данных рядом с тестами

Добавьте сервис и дождитесь его готовности:

```yaml
  tests:
    depends_on:
      postgres:
        condition: service_healthy
    environment:
      - POSTGRES_HOST=postgres
      - POSTGRES_PORT=5432
      - POSTGRES_USER
      - POSTGRES_PASSWORD

  postgres:
    image: proget.inc.elara.local/your-feed/postgres:18.1
    environment:
      - POSTGRES_USER
      - POSTGRES_PASSWORD
    healthcheck:
      test: ["CMD", "pg_isready", "-U", "${POSTGRES_USER}", "-d", "postgres"]
      interval: 5s
      timeout: 3s
      retries: 5
      start_period: 10s
```

В `.env.default`:

```
POSTGRES_USER=test
POSTGRES_PASSWORD=test
```

И обязательно в `test_cfg.xml`. Без этого база не стартует. При первом запуске
она создаёт свой каталог данных, а мы снимаем с контейнеров все права:

```xml
  <privileges>
    <service name="postgres" cap_add="CHOWN DAC_OVERRIDE FOWNER SETGID SETUID"/>
  </privileges>
```

В самом compose `cap_add` запрещён. Там можно попросить что угодно. В
`test_cfg.xml` список закрытый: восемь прав, ничего сверх них выдать нельзя.

### Пароли

В `.env.default` их класть нельзя. Этот файл лежит в git. Объявите в
`test_cfg.xml`:

```xml
  <secrets>
    <secret name="db_password" services="postgres"/>
  </secrets>
```

Имя секрета это имя файла. Разрешены маленькие буквы, цифры, подчёркивание.
В `services=` перечислите, каким сервисам он нужен. Не указали: значение
увидит только главный сервис.

Пароль приедет файлом в `/test/secrets/db_password`, только на чтение. Многие
образы умеют читать пароль из файла. Ищите переменные вида
`POSTGRES_PASSWORD_FILE`.

Локально каталог с паролями передаётся ключом:

```sh
./run_local.sh <набор> --repo <ваш репозиторий> --secrets <каталог с файлами>
```

В CI файлы кладёт отдельный шаг сборки. После прогона они стираются.

Проверки строгие. Объявили секрет, а файла нет: прогон не начнётся. Не передали
каталог: тоже. Так сделано специально. Пустое значение внутри контейнера
привело бы к странному падению тестов, и причину пришлось бы долго искать.

### Локальные значения, которые не хочется коммитить

Положите рядом `.env.local`. Он перекрывает `.env.default` и читается только
при локальном запуске. Добавьте его в `.gitignore`. Если он всё-таки попадёт
в репозиторий, на сервере его проигнорируют и напишут об этом в лог.

## Справочник

Каталоги внутри контейнера:

| Путь | Что это |
|---|---|
| `/test/output` | сюда пишете отчёты, отсюда их забирают |
| `/test/input` | то, что перечислено в `<inputs>`. Только чтение |
| `/test/secrets` | пароли файлами. Только чтение |

Пути в `<outputs>` считаются от `/test/output`. Атрибут `dest` в `<inputs>`
считается от `/test/input`.

Переменные, доступные всегда: `TEST_INPUT`, `TEST_OUTPUT`, `TEST_OS`,
`TEST_ARCH`, `TEST_CONFIG_NAME`, `BUILD_NUMBER`, `VCS_REVISION`.

Форматы отчётов: `trx` для .NET, `junit` для gtest и других, `cobertura` для
покрытия, `raw` для любого файла. Незнакомый тип отчёта прогон не ломает. Файл
просто сохранится.

Запрещено в compose: `build:`, проброс папок с хоста, `ports:`,
`container_name`, `restart`, `privileged`, `cap_add`, сеть и PID хоста, образы
не из ProGet, теги `latest`.

## Что ещё не решено

- какая конфигурация в TeamCity будет запускать наборы, решает лид;
- в какой фид ProGet класть образы с тестами, согласуется;
- arm-слоты: механика готова, нужны образы под эти архитектуры;
- Windows: второй этап.
